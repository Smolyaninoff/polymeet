# PolyMeet: материал к защите модульного тестирования

## 1. Цель и границы этапа

Цель — проверить отдельные правила приложения на правильных, ошибочных и граничных данных. Модульный тест вызывает функцию или небольшой сервис и сравнивает результат с ожидаемым. Для таких проверок не требуется запускать всё приложение.

В этом документе приведены только результаты **модульного тестирования**. Интеграционное, сквозное и нагрузочное тестирование рассматриваются отдельно: приведённые цифры ничего не доказывают о работе системы под нагрузкой или о взаимодействии реальных сервисов.

## 2. Что использовали

| Инструмент | Для чего |
|---|---|
| `pytest` и `pytest-asyncio` | запуск модульных и асинхронных тестов Python |
| `pytest-cov` / `coverage.py` | учёт выполненных строк и ветвлений выбранных модулей |
| `unittest.mock` | проверка сервиса чата с заменой репозитория тестовым объектом |
| `fakeredis` и `respx` | имитация Redis и HTTP-ответов внешнего геокодера внутри отдельных тестов |
| `Vitest` | проверка функций фронтенда на TypeScript |
| Docker Compose | одинаковый запуск тестов на машине с Docker и в CI |

Тесты не подключаются к рабочей базе и не отправляют запросы настоящему геокодеру. При проверке дат используется фиксированное время, а не предположение о текущем дне.

## 3. Как запускать

Из корня проекта:

```bash
./run.sh test-unit
```

Скрипт собирает тестовые образы и последовательно запускает `pytest tests/unit` и `vitest run`. Контейнеры с PostgreSQL, Redis, API и воркером при этом не поднимаются. Оба набора запускаются даже при ошибке одного из них; итоговый код команды будет ненулевым, если упал хотя бы один набор. Одноразовые контейнеры и сеть после прогона удаляются.

Результаты находятся в `reports/unit/`:

- `backend.xml` — результаты pytest в формате JUnit;
- `frontend.xml` — результаты Vitest в формате JUnit;
- `coverage.xml` — машиночитаемый отчёт coverage.py;
- `htmlcov/index.html` — подробный отчёт по выбранным модулям: можно открыть в браузере и перейти к строкам каждого файла.

Каталог `reports/` не входит в Git: это результат конкретного запуска. В GitHub Actions те же отчёты сохраняются как артефакт `unit-test-reports`. Автоматический прогон CI появится после публикации изменений; до этого результат подтверждается локальным запуском.

## 4. Какие правила проверяем

### Встречи

Файл `backend/tests/unit/test_meeting_rules.py` проверяет функции из `app/services/meeting_rules.py`:

- черновик видит организатор, остальные статусы видны и другим пользователям;
- будущий черновик можно опубликовать, а уже начавшуюся встречу — нельзя;
- отменённую или завершённую встречу нельзя произвольно вернуть в опубликованную;
- количество мест нельзя уменьшить ниже числа уже принятых участников;
- название, адрес и подсказка к адресу очищаются от лишних пробелов; слишком короткие значения отклоняются.

Для статусов применяется параметризация: варианты текущего и нового статуса и времени проверяются отдельно. Результат теста — либо ожидаемый статус, либо ожидаемая ошибка.

### Заявки и лист ожидания

Файл `backend/tests/unit/test_application_rules.py` проверяет чистые правила из `app/services/application_rules.py`:

- на будущую опубликованную встречу может подать заявку другой пользователь, но не сам организатор;
- новая заявка становится принятой при автоприёме и наличии места, ожидающей — при ручном рассмотрении, либо попадает в лист ожидания при заполненной встрече;
- последнее место можно занять, а принять заявку сверх вместимости нельзя;
- отзыв принятой заявки освобождает место, а отзыв ожидающей заявки не меняет число принятых;
- при освобождении или добавлении мест число продвигаемых заявок ограничено количеством свободных мест и длиной листа ожидания.

Правила переходов проверяются на нескольких статусах, решениях и вариантах заполненности. Порядок продвижения в реальной базе этим модульным тестом не проверяется.

### Чат

Файл `backend/tests/unit/test_chat_service.py` проверяет сервис из `app/services/chat_service.py` с подставным репозиторием. Если доступ разрешён, сервис запрашивает сообщения или сохраняет новое; если нет — возвращает ошибку и не обращается к операциям чтения или записи. Отдельно проверяется очистка текста от пробелов и отклонение пустого сообщения или сообщения длиной более 2000 символов.

Подставной репозиторий нужен, чтобы проверить решение сервиса отдельно. Он **не подтверждает**, что реальные запросы к базе и права доступа на уровне API работают правильно: это задача интеграционного этапа.

### Авторизация, пагинация и геокодирование

Другие файлы `backend/tests/unit/` содержат проверки нормализации и правил авторизации, JWT и срока действия токенов, ограничения числа неудачных входов, курсоров пагинации, нормализации адресов, повторных попыток и обработки недоступности внешнего сервиса. Например, тесты пагинации проверяют некорректные и повреждённые курсоры, а тесты геокодирования используют контролируемые HTTP-ответы.

### Фронтенд

Тесты в `frontend/src/lib/*.test.ts` проверяют:

- `validateMeetingForm`: обязательные поля, дату в будущем, целое число мест от 2 до 100 и границы диапазона;
- `filterMeetings`: поиск без учёта регистра, совместное действие фильтров, поведение при неизвестном расстоянии;
- `selectMyEvents`: разделение будущих встреч по роли и перенос прошедших, отменённых и завершённых встреч в историю.

Эти тесты вызывают функции напрямую. Они не являются автоматическими проверками браузера и не подтверждают работу реальной карты или внешних сервисов.

Параметризованный тест считается несколькими проверками: например, один тест статусов запускается с разными сочетаниями параметров. Поэтому 231 — число выполненных случаев pytest, а не число вручную написанных функций.

## 6. Что означает покрытие 100%

В команде запуска явно перечислены четыре модуля:

1. `app.services.meeting_rules`;
2. `app.services.application_rules`;
3. `app.services.chat_service`;
4. `app.core.pagination`.

Для них включён учёт ветвлений (`branch = true` в `backend/pyproject.toml`). В отчёте показано, что во время данного прогона выполнены все 117 учитываемых строк и все 40 учитываемых исходов ветвлений этих четырёх файлов. Чтобы добиться этого результата, для условий подобраны положительные и отрицательные примеры, граничные значения и допустимые и запрещённые переходы. Для проверки доступа к чату подставной репозиторий позволяет отдельно проверить разрешённый и запрещённый доступ.

**Это не 100% покрытия всего бэкенда и тем более не всего проекта.** Модели, API, работа с PostgreSQL и Redis, другие сервисы и интерфейс в указанный процент не входят. Высокое покрытие показывает, какой код был выполнен, но не гарантирует правильность всех требований и не заменяет проверку взаимодействий, ошибок сети или нагрузки.

## 7. Как показать на защите

1. Объяснить, что на данном этапе проверяются отдельные функции и правила, без настоящей базы и внешнего геокодера.
2. Открыть `backend/tests/unit/test_application_rules.py` и показать пример с последним свободным местом: при 4 принятых из 5 заявка принимается, при 5 из 5 возникает ошибка вместимости.
3. Открыть `frontend/src/lib/validateMeetingForm.test.ts` и показать проверку граничных значений 2 и 100 мест и недопустимых значений.
4. Запустить `./run.sh test-unit`, дождаться результатов обоих наборов.
5. Открыть `reports/unit/htmlcov/index.html`, показать список четырёх файлов и перейти к одному из них. Уточнить, что 100% относится только к этим файлам.
6. Отметить, что взаимодействие с реальной базой, браузерные сценарии и нагрузка — предмет следующих проверок.
